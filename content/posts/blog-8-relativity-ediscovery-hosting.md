# Relativity eDiscovery Hosting: What Firms Need to Decide Before 2028

Relativity eDiscovery hosting is no longer a simple cloud-versus-server choice. Relativity’s current policy changes what firms can do with new matters after 2027. Existing Server matters may remain supported, but new work moves toward Relativity aiR, subject to limited exceptions.

That distinction should shape every hosting review for 2027. A firm must separate legacy work from future matters. It must also compare internal infrastructure, partner services, migration labor, and long-term support. This guide turns those questions into a practical buying framework.

## Key Takeaways

The current policy sets a firm deadline for new work, not an unconditional Server shutdown. These points should guide the first planning meeting.

* **New matters change in 2028.** Relativity says new matters and workspaces will move to aiR in 2028, with limited exceptions.  
* **Existing matters can remain.** Current Server matters may continue with maintenance updates and security patches.  
* **Server keeps internal duties.** The hosting team remains responsible for infrastructure, licensing, scaling, backups, and operations.  
* **Partner scope needs detail.** A partner listing does not define migration work, support hours, pricing, or accountability.  
* **Costs need matched assumptions.** Compare the same data volume, processing load, support level, and retention period.  
* **Migration starts with inventory.** Matter status, custom applications, integrations, and exports affect the work required.

## Start With the Matter, Not the Hosting Label

A useful Relativity eDiscovery review begins with the work that must run. “Cloud” and “Server” are too broad for an early decision. The team needs a matter inventory, expected data volumes, review demands, integrations, and service requirements.

Start by separating new matters from existing ones. Relativity’s [Server 2028 policy](https://www.relativity.com/server-policy/) allows new Server matters through December 31, 2027. The same page says existing matters may stay on Server after that date. It also states there is no current plan to discontinue Server.

That policy creates two planning tracks. Each track needs its own owner, budget, and target date.

## Track One: New Matters and Workspaces

New work should assume a cloud-first destination from 2028. That does not mean every firm follows one identical route. Geography and certain customer conditions may create exceptions. Firms should request written confirmation for their exact position.

For 2027 planning, define which matters might open near the deadline. Then set a cutover rule before intake teams face a live decision. The rule should name the approved platform, provider, data region, and escalation owner.

## Track Two: Existing Server Matters

Legacy matters need a different test. Some can remain because they are near closure. Others may run for years and need continued investment. A third group may benefit from earlier migration because its workflows depend on future cloud features.

Classify each matter using these factors:

* **Expected life:** Estimate closure, appeal, investigation, or retention dates.  
* **Active workload:** Record users, review pace, productions, and processing demand.  
* **Technical dependencies:** List custom applications, scripts, integrations, and authentication methods.  
* **Export needs:** Define required formats, audit records, and chain-of-custody evidence.  
* **Risk level:** Note privilege, residency, confidentiality, and client restrictions.

The same inventory discipline supports a [controlled legal-AI pilot](https://verdictpoint.org/legal-tech/harvey-legal-ai-pilot/). Both projects fail when technical dependencies appear late.

## Compare Cloud, Server, and Partner Delivery

The hosting route decides who handles each operational task. It also changes which costs appear on the invoice. Use the matrix below to keep those responsibilities visible.

| Decision Area | Relativity aiR | Relativity Server | Partner-Assisted Route |
| :---- | :---- | :---- | :---- |
| **Platform infrastructure** | Relativity-managed cloud platform | Firm or provider-managed environment | Split by contract and service scope |
| **New matters after 2027** | Expected default, subject to exceptions | Generally restricted under current policy | Depends on the underlying platform |
| **Existing matters** | Migration choice based on need | May continue under current policy | Provider may support either path |
| **Upgrades and maintenance** | Platform service responsibility | Hosting team retains major duties | Contract must assign each duty |
| **Custom workflows** | Validate compatibility and replacement | Existing tools may continue | Partner may assess or rebuild them |
| **Cost visibility** | Quote, usage, storage, and services | Infrastructure, licenses, people, and support | Quote plus exclusions and change fees |
| **Best buyer question** | What is included in the commercial offer? | Can we support this safely through matter closure? | Who owns each migration and support task? |

⟧

The partner route is not a separate platform by itself. A partner may sell services around cloud migration, operations, or managed review. Relativity’s [partner directory](https://www.relativity.com/partners/) confirms available routes. It does not validate a specific partner’s scope or fees.

Ask each provider for a responsibility schedule. It should name the party responsible for backups, incident response, user support, upgrades, exports, and migration validation.

## Understand the Real Work Behind Relativity Server

Server ownership includes more than a software license. Relativity’s [Server 2026 system requirements](https://help.relativity.com/Server2026/Content/Installing_and_Upgrading/System_requirements/System_requirements.htm) describe scalable infrastructure built on .NET and Microsoft SQL Server. The documentation also covers storage, workers, load balancing, backup planning, and disaster recovery.

Those requirements do not create one universal cost. They show why firms need a full operating model. Hardware alone cannot capture the staff time and resilience work involved.

## Infrastructure Costs to Include

Price comparisons should include every resource needed to run the environment. Use current quotes instead of standard assumptions.

* **Compute and storage:** Include production, testing, backups, indexes, and temporary processing space.  
* **Microsoft licensing:** Account for Windows, SQL Server, and any required Office components.  
* **Security operations:** Include monitoring, patching, access reviews, and incident response.  
* **Resilience:** Price backups, recovery testing, failover, and business continuity.  
* **Administration:** Count engineering, database, application, and user-support time.  
* **Upgrade work:** Include testing, deployment, rollback planning, and custom application checks.

The organization must also decide how long it will maintain these skills. A shrinking Server estate can cost more per matter. Fixed overhead then spreads across fewer active workspaces.

## Operational Questions to Answer

Technical ownership needs named people and service targets. A hosting plan remains incomplete until those details appear in writing.

Ask the following questions before renewing Server capacity:

1. Who approves platform and security updates?  
2. How often does the team test backups and recovery?  
3. Which custom tools depend on the current version?  
4. What happens when a key administrator leaves?  
5. Which matters require support beyond 2028?  
6. What evidence will clients request during security reviews?

These questions often expose the real constraint. The issue may be staffing, not hardware.

## Build a Like-for-Like Cost Comparison

Relativity eDiscovery pricing cannot be reduced to one public number. Quotes may reflect platform scope, storage, processing, users, support, partner services, and migration. Server costs also vary by workload and internal accounting.

Use one workload profile for every option. Then request pricing against the same assumptions.

| Cost Input | What to Record | Why It Changes the Result |
| :---- | :---- | :---- |
| **Active data** | Average and peak volume | Storage and review demands may differ |
| **Processing** | Monthly volume and peak timing | Burst capacity affects service design |
| **Users** | Concurrent and named users | Licensing and support may use different units |
| **Retention** | Matter and archive periods | Long retention can dominate storage costs |
| **Support** | Hours, response targets, escalation | Basic and managed services are not equivalent |
| **Migration** | Exports, transforms, validation, retries | A platform quote may exclude project work |
| **Custom tools** | Rebuild, replace, or retire | Compatibility work may drive the schedule |

⟧

Do not compare a cloud subscription with Server licensing alone. Add people, facilities, security, recovery, upgrades, and downtime exposure. For a partner quote, list every exclusion. Then assign an internal owner to each excluded task.

## Plan Migration Around Evidence and Acceptance Tests

A migration succeeds when the destination matches approved source records. Moving bytes is only one part. Teams must confirm users, permissions, metadata, searches, productions, and audit history.

Before choosing dates, complete this readiness checklist:

* **Inventory matters:** Record status, owner, size, region, and target disposition.  
* **Map dependencies:** List applications, scripts, integrations, and identity controls.  
* **Define exports:** State formats, metadata fields, load files, and audit requirements.  
* **Set validation rules:** Choose record counts, hashes, sampling, and exception limits.  
* **Test permissions:** Confirm groups, ethical walls, client restrictions, and external access.  
* **Plan retention:** Decide what moves, stays, archives, or reaches approved deletion.  
* **Assign support:** Name vendor, partner, and firm owners for every phase.

The schedule should include a pilot matter. Choose one with realistic complexity but manageable risk. Record every defect and correction. Those findings improve the plan for later waves.

The same discipline applies to [Everlaw review and collaboration](https://verdictpoint.org/legal-tech/everlaw-ediscovery-document-review/) assessments. Workflow fit depends on real matter steps, not feature lists.

## Treat 2027 as the Decision Year

The 2028 rule makes 2027 a practical cutover year. Firms need enough time for procurement, security review, contracting, technical testing, and staff training. A late decision compresses every one of those tasks.

Use four milestones to control the work:

1. **Inventory approved:** Matter owners confirm status, dependencies, and restrictions.  
2. **Commercial scope approved:** Quotes use matching workloads and service definitions.  
3. **Pilot accepted:** The team meets written migration and workflow tests.  
4. **Cutover rule published:** Intake teams know where new matters will open.

Broader [legal technology statistics](https://verdictpoint.org/legal-tech/legal-technology-statistics/) can frame adoption trends. They should not replace a firm-specific capacity and risk review.

## Govern the Mixed Environment During Transition

Many firms will run cloud and Server matters at the same time. That mixed period creates operational risks beyond migration. Staff may use different tools, support routes, and security procedures for similar work.

Create one transition register for both environments. The register should identify every active matter, its platform, its support owner, and its planned disposition. Review it monthly during the cutover period.

The operating team should also standardize these controls:

* **Intake routing:** Tell staff which platform accepts each new matter type.  
* **Access review:** Check users and groups across both environments on one schedule.  
* **Incident handling:** Publish separate technical steps under one escalation policy.  
* **Change control:** Record upgrades, configuration changes, and migration work together.  
* **Client reporting:** Explain platform differences without making unsupported security comparisons.  
* **Knowledge transfer:** Document Server duties before experienced administrators leave the role.

Avoid running two informal governance systems. A single oversight group can compare risks across platforms. It can also decide when a legacy workspace should stay, migrate, archive, or close.

Set an exception process for matters that miss the normal schedule. Each exception should name the business reason, risk owner, controls, and review date. Open-ended exceptions can keep expensive infrastructure alive long after the original need disappears.

## Frequently Asked Questions

These answers reflect public documentation checked in September 2026. Firms should confirm contract terms before acting.

## Is Relativity Server Shutting Down in 2028?

No. Relativity says existing Server matters may continue with maintenance updates and security patches. The policy mainly changes where new matters open.

## Can a Firm Open New Server Matters During 2027?

Relativity says licensed customers may open new Server matters through December 31, 2027. Limited customer and geographic exceptions may apply afterward.

## Does Relativity eDiscovery Have Public Standard Pricing?

Public pages do not provide one universal price for every deployment. Request matched quotes that include storage, processing, support, and migration.

## Should Every Existing Matter Move to the Cloud?

No single rule fits every matter. Consider lifespan, risk, dependencies, cost, and future workflow needs before choosing.

## What Should a Partner Proposal Include?

It should assign migration, validation, security, support, exports, and incident duties. It should also list exclusions and change fees.

## Make the Hosting Decision Defensible

A sound hosting plan separates policy facts from sales claims. It also separates new work from legacy matters. Build the inventory first, compare equal workloads, and assign every operational duty.
